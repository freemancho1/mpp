# MPP (Muse Pulse Project)

> 한국 주식 데이트레이딩의 매매 타이밍을 포착하고 주문까지 자동화하는 시스템 MPS(Muse Pulse System)의 설계·개발 기준 문서
> 이 문서는 프로젝트의 모든 답변과 작업의 기준이다. 결정이 바뀌면 이 문서를 먼저 고친다.
> 최종 수정: 2026-10-14

---

#### 1. 프로젝트 개요

##### 1.1 정의

- 프로젝트 이름: MPP (Muse Pulse Project)
- 시스템 이름: MPS (Muse Pulse System)
- 목적: 한국 주식시장(KOSPI/KOSDAQ)에서 데이트레이딩 매매 타이밍을 포착하고, 주문 집행까지 자동화한다
- 진행 방식: 설계와 개발을 하나의 프로젝트에서 함께 진행한다 (2026년 10월, 기존 설계·개발 프로젝트를 통합)

##### 1.2 확정된 범위

- 매매 스타일: 데이트레이딩. 당일 진입, 당일 청산, 오버나이트 포지션 없음
- 대상 종목
  - 1단계: 삼성전자(005930) 단일 종목으로 전 과정을 완성한다
  - 이후: 사용자가 선택한 N개(N<10) 종목으로 확장한다
  - 시장 전체 스캔은 하지 않는다
- 브로커: 한국투자증권 KIS Open API (신청 예정, 2026-10-14 기준 미신청)
- 시장: 1단계는 KRX 정규장 기준. 넥스트레이드(NXT) 프리·애프터마켓은 확장 옵션

---

#### 2. 시스템 목표

- 목표 함수는 적중률이 아니라 **거래비용 차감 후 위험 대비 수익**이다
- 비용 전제
  - 2026년 기준 매도 시 거래세 0.20% (코스피·코스닥 동일)
  - 수수료와 슬리피지를 더한 왕복 비용은 대략 0.25~0.35%
- 비용 구조상 잦은 초단타는 불리하다. **하루 0~3회의 선별된 거래**를 기본으로 한다

---

#### 3. 데이트레이딩 전략 설계

##### 3.1 4단 의사결정 구조

- ① 장전 컨텍스트
  - 미국 증시 마감, 환율, 야간 선물, 공시·뉴스를 종합한다
  - 당일 레짐(추세일/횡보일/고변동/거래회피)과 종목별 편향을 판정한다
- ② 셋업 탐지
  - 시간대별로 검증된 진입 후보를 찾는다
  - 후보 예: 시가 범위 돌파, VWAP 눌림·회귀, 수급 급변(체결강도·호가 불균형), 캔들·차트 패턴
- ③ 진입 승인 (메타 판단)
  - 셋업이 실제로 이길 확률과 기대 손익을 모델이 추정한다
  - 비용 차감 후 기대값이 기준을 넘을 때만 진입한다
  - 수익의 핵심은 이 "거르는 단계"다. 셋업은 넓게 찾고 진입은 엄격하게 고른다
- ④ 청산
  - 변동성(ATR 등)에 비례한 목표가·손절가
  - 추적 손절, 본전 손절
  - 장 마감 전 강제 청산

##### 3.2 이중 관점 신호

- 수치 관점: 가격, 거래량, 호가, 수급 피처
- 패턴 관점: 캔들·차트 패턴 인식
- 두 관점은 셋업 탐지와 메타 판단 단계에서 결합한다

##### 3.3 포지션·리스크 관리

- 포지션 크기는 모델 신뢰도와 변동성에 비례시킨다
- 리스크 한도
  - 일일 손실 한도
  - 일일 최대 거래 횟수
  - 연속 손실 시 당일 거래 중단
  - 긴급 정지(kill switch)

#### 4. 모델·검증 설계

##### 4.1 라벨

- 변동성 비례 배리어와 장중 시간 제한을 가진 Triple Barrier 방식
- 승패는 비용 차감 후 손익 기준으로 정한다

##### 4.2 모델 구성

- 단순한 것부터 쌓고, 더 나을 때만 복잡한 것을 채택한다
- 기준 모델: 그래디언트 부스팅(LightGBM 등) 기반 메타 판단 모델
- 패턴 트랙: 1D-CNN, 소형 Transformer, 또는 시계열 파운데이션 모델 임베딩. 기준 모델보다 나을 때만 채택
- 텍스트: LLM으로 공시·뉴스를 유형·중요도·방향으로 구조화한다. 장전 컨텍스트와 위험 필터로 쓰고, 실시간 알파 신호로는 쓰지 않는다
- 강화학습: 위 구조가 검증된 뒤에 검토한다

##### 4.3 검증 원칙

- 미래 정보 차단: 모든 피처는 해당 시점에 실제로 알 수 있었던 값만 쓴다
- 워크포워드 검증, 라벨 중첩을 고려한 purged 분할
- 여러 전략을 시험한 만큼 성과를 할인해서 본다 (과최적화 경계)
- 백테스트에 거래세·수수료·슬리피지·호가단위·상하한가·체결 가능성을 반영한다

##### 4.4 검증 단계

- 백테스트 → 실시간 모의투자(최소 4~8주) → 소액 실전 → 증액
- 실계좌 연결은 모의투자 기준을 통과한 뒤에만 다룬다

---

#### 5. N종목 확장 설계

- 처음부터 모든 모듈이 종목코드를 파라미터로 받는다. 종목 목록은 설정 파일로 관리한다
- 모델은 여러 종목을 함께 학습하는 공용 모델을 기본으로 하고, 종목별로 임계값·보정만 따로 둔다
- 포트폴리오 계층
  - 동시 보유 종목 수 상한
  - 종목당 자금 비중 상한
  - 같은 업종 쏠림 제한
  - 전체 일일 손실 한도
- 종목 선정 기준: 유동성, 호가 스프레드 대비 변동성, 장중 변동폭
- 실시간 구독은 종목당 체결·호가 2건이다. KIS WebSocket 세션당 등록 상한은 API 신청 후 공식 문서로 확인한다

---

#### 6. 데이터·운영 설계

##### 6.1 데이터

- 실시간 시세(체결·호가): KIS WebSocket
- 주문·잔고: KIS REST
- 과거 분봉은 확보에 한계가 있다. API 승인 직후부터 체결·호가를 자체 수집해 축적한다
- 이 수집기는 모델보다 먼저 가동한다. 데이터는 시간이 지나야만 쌓이기 때문이다
- 모든 데이터는 데이터 루트 `~/datas/mpp`에 저장한다 (구성은 7.5절)

##### 6.2 기술 구성 (개인 운영 규모)

- 연구 데이터: Parquet + DuckDB/Polars
- 거래 원장: SQLite 또는 PostgreSQL
- 실시간 엔진: 단일 프로세스 비동기 구조
- 배치 작업: 간단한 스케줄러
- 알림: 텔레그램
- 무거운 인프라(Kafka, Airflow 등)는 필요가 입증될 때만 도입한다

#### 7. 개발 방식

##### 7.1 도구별 역할

- 설계: claude.ai MPP 프로젝트
  - 전략·모델·데이터·리스크 결정, 대안 비교, 설계 문서 작성
  - Claude Code에 맡길 작업 정의, 구현 결과 검토, 오류 원인 분석
- 구현·테스트: VS Code의 Claude Code (로컬 Ubuntu)
  - 코드 작성, 수정, 단위 테스트, 커밋
  - 저장소의 `CLAUDE.md`와 `docs/` 설계 문서를 따른다
- 장시간 실행 확인: 터미널 (Claude Code CLI + 직접 실행)
  - 데이터 수집기, 긴 백테스트, 모의투자 엔진을 실행하며 로그를 확인한다
- 클라우드 실행(웹·모바일 Claude Code)은 문서 정리·순수 로직 수정·코드 리뷰 등 보조 용도로만 쓴다

##### 7.2 작업 흐름

- ① 설계: claude.ai 프로젝트에서 결정하고 설계 문서로 정리한다
- ② 반영: 확정 문서를 GitHub 저장소 `docs/`에 커밋한다. 저장소 문서가 유일한 기준 원본이다
- ③ 구현: Claude Code에 작은 단위로 작업을 맡긴다. 큰 작업은 Plan Mode로 계획을 먼저 확인한다
- ④ 기록: 구현 중 설계를 바꾸면 `docs/decisions/`에 "무엇을, 왜"를 남긴다
- ⑤ 동기화: 단계가 끝날 때마다 변경된 문서를 claude.ai 프로젝트 지식에 반영한다

##### 7.3 경로와 저장소 구성

- 프로젝트 루트: `~/projects/mpp` (Git 저장소, MPS 소스와 문서)
- 데이터 루트: `~/datas/mpp` (저장소 밖, Git에 넣지 않음)
- 버전은 폴더로 나누지 않고 Git으로 관리한다
  - 동작하는 지점마다 태그를 붙인다. 예: `v0.1-collector`, `v0.2-backtest`, `v1.0-paper`
  - 큰 실험·재작성은 브랜치에서 진행하고 검증 후 `main`에 합친다
  - 모의·실전 운영은 태그 기준으로 실행한다

##### 7.4 프로젝트 루트 구성 (`~/projects/mpp`)

- `README.md`: 이 문서
- `CLAUDE.md`: Claude Code용 작업 지침
- `docs/`: 설계 문서, `index.md`, `decisions/` 결정 기록
- `config/`: 종목 목록, 리스크 한도, 비용 모델, 실전/모의 전환, 경로 설정
- `src/mps/`: 계층별 모듈
  - `collect/`: KIS 실시간·REST 수집
  - `features/`: 피처·라벨
  - `models/`: 셋업 탐지, 메타 판단, 패턴 트랙
  - `backtest/`: 비용 반영 시뮬레이터
  - `engine/`: 실시간 의사결정 엔진
  - `execution/`: 주문·포지션·리스크
  - `notify/`: 알림
  - `common/`: 설정, 시간대, 거래 캘린더, 로깅
- `tests/`: 미래 정보 누출, 비용 계산, 라벨링, 리스크 한도 테스트를 우선 작성한다
- `notebooks/`: 연구·분석용. 운영 코드와 분리한다
- `scripts/`: 수집기·백테스트·모의투자 실행 진입점
- `.env`: API 키 (Git 제외)

##### 7.5 데이터 루트 구성 (`~/datas/mpp`)

- `raw/`: 수집 원본. 수정하지 않는다
  - `ticks/`: 실시간 체결
  - `orderbook/`: 실시간 호가
  - `daily/`: 일봉·수급 등 일 단위 데이터
  - `text/`: 공시·뉴스 원문
- `bars/`: 원본에서 집계한 분봉
- `features/`: 피처·라벨 데이터셋 (생성 버전별)
- `models/`: 학습된 모델 산출물 (버전별)
- `backtests/`: 백테스트 결과
- `ledger/`: 신호·주문·체결 거래 원장 DB
- `logs/`: 실행 로그
- 원칙: `raw/`는 추가만 하고, 나머지는 `raw/`에서 언제든 다시 만들 수 있어야 한다

##### 7.6 개발 단계

- Phase 0: KIS API 신청, 모의투자 계좌 준비, 체결·호가 수집기 가동
- Phase 1: 삼성전자 대상 피처·셋업·라벨, 비용 반영 백테스트 시뮬레이터
- Phase 2: 기준 모델(메타 판단) + 패턴 트랙, 워크포워드 검증
- Phase 3: 실시간 모의투자 운영 (최소 4~8주)
- Phase 4: 소액 실전 → 증액
- Phase 5: N종목(N<10) 확장 + 포트폴리오 계층

##### 7.7 개발 환경

- Ubuntu 24.04, VS Code + Claude Code 확장, Jupyter, Anaconda 환경 `ai_dev`
- GitHub 저장소: MPP 전용 저장소를 새로 만든다 (기본 브랜치 `main`). 이전 MPS 코드는 섞지 않는다

#### 8. 답변·작업 규칙

##### 8.1 claude.ai 프로젝트에서의 작업 모드

- 설계 모드 (기본)
  - 개념, 방법론, 설계, 기획 문서를 다룬다
  - 코드는 쓰지 않고 흐름과 인터페이스(입출력 형태)까지만 제시한다
- 개발 지원 모드
  - 사용자가 명시적으로 요청할 때만 들어간다
  - Claude Code 작업 지시문 작성, 코드 검토, 오류 분석, 필요 시 코드 예시
  - 설계와 다르게 가야 하면 차이와 이유를 먼저 말한다
- 어느 모드인지 애매하면 한 줄로 먼저 확인한다

##### 8.2 답변 원칙

- 새 주제는 이론과 개념을 먼저 설명한 뒤 구체화한다
- 방법론 선택지가 있으면 대안, 장단점, 추천과 근거를 함께 제시한다
- 세율, API 사양, 라이브러리, 규정처럼 바뀔 수 있는 정보는 최신 상태를 확인한 뒤 답한다
- 사용자의 지적이 맞으면 바로 인정하고 정정한다. 근거 없는 추천은 하지 않는다

##### 8.3 문서 작성 규칙

- 한국어로 쓴다
- 제목은 `####`/`#####` 계층, 내용은 글머리표로 쓴다. 표는 요청할 때만 쓴다
- 기획 문서는 주제별 파일로 나누고 인덱스 파일에서 연결한다

#### 9. 안전·주의 사항

- 특정 매매에 대한 확정적 투자 권유는 하지 않는다. 시스템 설계·검증 관점에서 다룬다
- API 키·토큰은 `.env`에 두고 Git에서 제외한다. 평문으로 다루지 않으며 Claude Code가 읽지 못하게 권한을 막는다
- 개발 중에는 모의투자 키만 쓴다. 실전 키는 모의투자 검증 통과 후 사람이 직접 넣는다
- Claude Code는 시스템을 만드는 도구다. 완성된 매매 엔진은 Ubuntu 서비스로 따로 운영하고, 장중 주문 흐름에 Claude Code가 개입하지 않게 한다
- 리스크 한도·긴급 정지 코드는 반드시 사람이 검토하고 테스트로 확인한다
- 실전 전환 전에 증권사 약관과 한국거래소 알고리즘 거래 관련 규정을 확인한다
